# Zyvor Payments: status against the brief

Legend: ✅ built and tested · 🟡 built, verified only against local simulators · ◐ partial · ❌ not built.
"Simulated" means the local mock provider (`zyvor-provider-mock`) or the in-process simulator. **Nothing here has run against a live provider.** One capability, Cashfree UPI intent and QR, has been run against Cashfree's own **sandbox** (see [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md)); every other provider path is simulator-only until you supply test credentials and run [REAL_SANDBOX.md](REAL_SANDBOX.md).

## Release 2a: security hardening and payment links
- **Rate limiting**: token buckets per API key and per client address (429 + `Retry-After`); behind proxies the address is counted from the right of `X-Forwarded-For` with `ZYVOR_TRUST_PROXY_HOPS`. In memory per replica.
- **API keys**: optional expiry, source-address allow-list (CIDR), `last_used_at`, and rotation with an overlap window (`POST /v1/api_keys/{id}/rotate`).
- **Webhook SSRF guard**: merchant webhook URLs must be https and public when saved, and the worker connects only to addresses it vetted at delivery time (`ZYVOR_ALLOW_PRIVATE_TARGETS=1` for sandboxes).
- **Opt-in dunning**: per-tenant policy in settings; the worker reminds overdue invoices with no live promise, once per repeat window.
- **Payment links**: fixed amount or an invoice's outstanding balance, caps, expiry, cancel; each opener gets their own intent. Console page, checkout landing page, and node/python/go SDK methods.
- **Supply chain**: `.github/workflows/security.yml` (cargo-deny, pnpm audit, gitleaks, CodeQL, Trivy, SBOM), Dependabot, actions pinned by SHA; `docs/zyvor/THREAT_MODEL.md`.
- **Cluster**: default-deny ingress NetworkPolicies and Pod Security `baseline` in the `zyvor` namespace. Verified on the k3s sandbox: checkout reaches the API but not Postgres or the provider simulator; HTTPS still works.
- **Audit chain**: the worker seals each tenant's audit events into a hash chain; `GET /v1/audit_events/verify` recomputes it and reports the first broken seal (editing, deleting or inserting inside a sealed range is detected, tested with a superuser bypass).
- **Master-key rotation**: ciphertext carries a key id; `ZYVOR_MASTER_KEY_PREVIOUS` keeps old data readable; `zyvor-api rekey [--dry-run]` re-seals every stored secret (idempotent; unreadable secrets are left untouched and reported). Pre-rotation blobs are still readable.
- **Console users**: named accounts (admin / finance / viewer) with Argon2id passwords, TOTP second factor with single-use recovery codes and replay protection, lockout after 5 failures (15 min), role-gated actions, and a People page. The deployment admin stays as break-glass only until the first named user exists; `CONSOLE_REQUIRE_MFA=1` forces enrolment. Verified in a browser: break-glass sign-in, create user, break-glass refused afterwards, MFA enrolment (this found and fixed a bug where recovery codes were never shown), code step at sign-in, recovery-code sign-in.
- **Reminder approvals and the AI assistant**: reminders can be drafted for a person to edit and approve (approving is what logs them and emits `invoice.reminder`); dunning can create drafts instead of sending (`dunning.requires_approval`). The optional AI assistant (`ZYVOR_AI_API_KEY`; off by default) only words drafts: it is given the merchant name, invoice number, amount, due date and counts, never customer details; its output is refused if it contains links, emails, threats or lacks the invoice number, falling back to the standard text; capped per tenant per month. Tested against a stand-in model server, **not** against the real API.
- **GST**: seller GSTIN in settings (checksum-validated), tax invoices from lines (HSN/SAC, quantity, unit price, standard slab) computing CGST+SGST within the state or IGST across states, buyer GSTIN from the customer or request, tax-proportional credit notes, `GET /v1/invoices/{id}/lines`, and `GET /v1/gst/gstr1?period=YYYY-MM` (B2B, B2C large/small, credit notes, HSN summary). A preparation aid: Zyvor does not file returns, generate IRNs/QR codes, handle e-way bills, exports, or cess. `GET /v1/invoices/{id}/einvoice` returns a DRAFT e-invoice JSON in the shape of IRP schema 1.1 for a B2B tax invoice (seller and buyer addresses are stored for it; it lists what is missing instead of guessing). That shape is written from the published field list and has NOT been run through the portal's validator or a GSP; the first real upload will show what needs adjusting.
- **Payouts**: vendors with encrypted bank details (lists show masks; full details only to `payouts:approve`, audited), payout requests that need a second person (no self-approval; a tenant threshold can waive it for small amounts), idempotent by your reference, a unique bank reference (UTR) per payout, ledger posting (Dr payouts / Cr bank) once on `mark_paid`, events, console page. **Zyvor does not move the money**: there is no payout-rail adapter, you make the transfer from your own bank and record it.
- **Webhooks v2**: an event catalogue (`GET /v1/events/catalogue`, with a debug assertion so no event can be emitted without being listed) and per-tenant subscriptions (`webhook_events`: exact types, families like `payment.*`, or `*`); events a merchant did not subscribe to are never queued. One endpoint per tenant still; the delivery log and replay were already there.
- **Instalment plans** (term fees, treatment plans): `POST /v1/installment_plans` splits an agreed total into dated invoices (exact split with the remainder on the last, month or day steps clamped to month end, all or nothing, idempotent by `external_ref`); the plan shows how much of each instalment is settled. This is the building block for the campus/clinic/factory templates.
- **Console settings page** (admin): collections (auto reminders, approval, channel, timing), approval thresholds for refunds and payouts, GST profile, webhook endpoint, write-only signing secret and event subscriptions from the catalogue. Verified in a browser: values load, saves apply, an invalid GSTIN is refused with the field kept.
- **Console billing forms**: add a customer (optional GSTIN), create an invoice (plain, or a GST tax invoice from HSN/SAC and rate with the tax added by the server), void an unpaid invoice, and create an instalment plan. Verified in a browser: instalments 333.33/333.33/333.35 for 1000.01; a GST invoice before a GSTIN is configured is refused with the input kept, then succeeds as ₹5,900.00 for a ₹5,000 price at 18%.
- **Exchange rates (reporting only)**: you record the INR-per-USD rate for a day (admin, one per day, immutable, never fetched from a market feed); `GET /v1/fx/convert` and the ageing report use the latest rate on or before the date, and the ageing shows each dollar bucket and a combined total in INR (null, not a guess, when no rate exists). The ledger stays per currency; `GET /v1/fx/exposure` values open dollar invoices at the rate on the day each was raised and at the report date and shows the difference (null when a rate is missing). It is a report: nothing is posted, the ledger is not revalued, and there is no realised gain or loss or any currency beyond INR and USD.
- **Merchant operations (Release 3)**: onboarding records (profile with PAN and GSTIN checks, document references, bank accounts with last four digits only; a second person verifies and reviews; payouts wait for approval once onboarding is started); counters within branches with counter-tied payment-link QR codes, a branch filter on payments and a daily branch summary; cash entries and an end-of-day closing with second-person sign-off (records only, cash is not posted to the ledger); a per-payment timeline with a plain sentence on where it stands; cash-due-by-week and refund-pattern insights (deterministic, no model). Found and fixed on the way: ids from another tenant were accepted on payment links, invoices, counters and cash entries because foreign keys skip row-level security. Open-amount payment links (the payer types the amount within limits you set; no coupon, split or fee on those) are built. API keys can be pinned to one branch (they then work only on the branch endpoints: payments, a payment's timeline, payment links, counters, cash entries, closings and the summary, all confined to that branch; every other endpoint refuses them, and rotation keeps the pin; created from the console's API keys page). A console cashier role (till page only: record cash and count; no sign-off) exists, and can be tied to one branch (the console forces that branch on the server and hides the others); that limit lives in the console, not the API, because the console's key is tenant-wide. The page-access rule was checked over HTTP against a production build, not yet end to end against a live API. Not built: the model-based reconciliation explainer, UPI AutoPay, soundbox, consumer UPI app. Zyvor is not a payment aggregator and does not verify identity; onboarding only records what a person checked.
- **Marketplace splits, bulk payouts and QR codes** (from comparing Indian gateways, see MARKET.md): shares per vendor on a payment or payment link, accrued on capture, reversed in proportion on refunds, a per-vendor balance (`GET /v1/vendors/{id}/balance`), balance-funded payouts that cannot overspend, `POST /v1/payouts/bulk` (all or none, repeat-safe), and `GET /v1/payment_links/{id}/qr.svg`. A lost dispute takes the same proportion back from each vendor (the loss is booked to adjustments, net of their share). Money still moves from your bank.
- **Risk limits**: per-tenant rules enforced before a payment reaches a provider: a ceiling on one payment, a cap on tries per payment, a cap on a customer's failed tries per hour, and refused UPI ids or whole handles. Every stop is audited and raises `payment.risk_blocked`. These are limits you choose, not fraud scoring.
- **Coupons and convenience fees** on fixed-amount payment links: percent or flat coupons (capped uses, expiry, deactivation, spent atomically with the payer's payment) and a fee the payer covers; the payer sees the breakdown, previewing a coupon spends nothing, and a coupon can never make a payment free. Verified in a browser: valid and invalid codes, the price clearing after a bad code (a bug found and fixed there), and the carry-through to checkout.
- **Checkout in six languages** (English, Hindi, Marathi, Tamil, Telugu, Bengali) on the payer's pages: `?lang=`, remembered choice, or browser language; a test keeps every language complete and every placeholder intact. Verified in a browser in Hindi and Tamil across the link page and the payment page. The translations are not yet reviewed by native speakers.
- **Console payouts**: vendors' split-payment balances, a "pay from their balance" option, and a bulk upload (`vendor, amount, purpose, reference` per line; names or ids; refuses lines with extra columns so `12,500` cannot silently become ₹12; keeps the text on an error; repeat-safe by reference). Verified in a browser.
- Still open from the plan: AI assist, payouts, multi-currency/FX, GST, vertical templates, webhooks v2.

## UPI AutoPay mandates (simulator only)

| Area | State | Notes |
|---|---|---|
| Mandate lifecycle: create, payer approves, refresh, pause, resume, revoke, expire | 🟡 | `POST /v1/mandates` and friends. The payer's approval is played by the simulator's test payer (`POST /v1/sim/mandate`, off unless `ZYVOR_SIM_PAYER=1`). A merchant pause is Zyvor's own hold; a provider revoke or decline always wins on refresh. |
| Scheduled debits | 🟡 | A debit is an ordinary payment attempt, so the ledger pair, `payment.*` events and unknown-outcome resolution are the existing ones. At most the mandate's cap; inside its dates and currency; at most one per frequency period; **never two on the same day** (`UNIQUE (mandate_id, due_date)`). |
| Pre-debit notice | 🟡 | The worker emits `mandate.debit_notified`; a debit goes out only when the notice is at least `ZYVOR_MANDATE_NOTICE_HOURS` old (default 24). **Zyvor does not message the payer**: the merchant or the provider must. |
| Failed debits | 🟡 | One retry the next day, then `failed` with `mandate.debit_failed`; the invoice stays open and the usual reminders carry on. |
| Auto-collect for subscriptions | 🟡 | Link a mandate to a subscription; each invoice is scheduled as a debit and marked paid when captured. Without an active mandate nothing changes. |
| iOS screens | 🟡 | Pay (scan, approve, taken debits, stop) and Merchant (create with QR, schedule, pause, resume, revoke, Run now) in `apps/ios`, against the simulator only. The payer sees debits taken, not upcoming ones. Run on phones: see the PR for what was checked. |
| Real providers | ❌ | No Cashfree Subscriptions or Razorpay recurring adapter. Their `mandates` capability is false, so a mandate request answers `no_route`. |
| The rules (notice window, per-debit ceiling default ₹15,000) | ◐ | Configurable, strict by default, **not verified against NPCI's current circular**; see [REGULATORY.md](REGULATORY.md). |

## Deviations from the brief
- **Rust instead of Go** for the backend (decision made with the owner: it keeps the tested ledger/idempotency/outbox code).
- JSON bodies for bank-statement and settlement import instead of file formats.

## The claim to prove in pilots
Fewer unresolved payments, less reconciliation work, faster integration. None of that is demonstrated yet; the tests prove correctness of the mechanisms, not customer outcomes.

- **Self-serve console (branch `ux/stripe-console`)**: public signup (`POST /v1/signup`), email sign-in per organisation (`POST /v1/console/login`, 12-hour role-scoped session key held in an encrypted cookie), Test/Live switch (`POST /v1/console/switch_env`; live opens once the business is approved and the approval is carried into the live tenant), a top bar, and a four-step onboarding stepper. With `ZYVOR_KYC_PROVIDER=simulator`, PAN, GSTIN and bank checks run when each is entered and a clean submission is approved without a person; anything else goes to the existing second-person review with the reasons shown. **The simulator is the only provider and verifies nothing real.** Not done: no email is sent (the signup verification token is only logged) and verification is not enforced at sign-in; session keys are not revoked at sign-out (they expire after 12 hours); no real KYC vendor; live-mode switching in the console exists only for email sign-ins.

- **Developer area (branch `ux/stripe-console`)**: an admin-only Developers page (quickstart in curl, Node, Python and Go for creating a payment, a webhook-signature check, and the endpoint status), `POST /v1/outbox/test` (queues a `webhook.test` event; needs a webhook URL; sent even if not subscribed), a "Send test event" button, and expandable payloads on the Webhooks page. The snippets never contain a key: the console deliberately does not show its session key. The SDKs are not published to a package registry. Not built: a sandbox control page for forcing provider outcomes (the simulators run outside the API), a request/API log, and per-attempt delivery history (the outbox keeps the attempt count and last error only). Webhooks is now admin-only in the console, matching the API's `admin` scope.

- **Roles and people (branch `ux/stripe-console`)**: an organisation's people live in its test tenant and sign in by email through a directory (`login_directory`, filled by signup and by adding a person on the People page; one email belongs to one organisation). Public sign-in always lands in test; live is reached only through the Test/Live switch, so a second factor cannot be skipped by asking for live. Session keys are scoped by role (admin: everything; finance: payments, refunds, billing, collections, payouts, disputes, reconciliation and onboarding writes but no key, user, settings or webhook administration; viewer: read-only on payments and reconciliation; cashier: payments, branch-pinned). Disabling a person, or setting their password, revokes their session keys in both environments at once. A person can set up their own second factor with their session key. A cashier's session stays in test (use a branch-limited API key at a live till). Console pages that the menu hides now also refuse the role when the address is typed in; the closing page works for a branch-limited cashier. Also added: an overview "Finish setting up" checklist for admins, an in-shell error and not-found page, and a phone layout (one-line menu strip). Checked in a browser as admin, finance, viewer and cashier against a local stack. Not done: people added by email exist only in test, so a self-serve organisation cannot give someone a role in live only; no email invitations (an admin sets an initial password); a 401 from a revoked session shows the error page rather than the sign-in page.

- **Email and invitations (branch `ux/stripe-console`)**: outgoing mail goes through a database queue (`mail_queue`) that the worker drains, with eight retries and a growing delay, then marks dead; the body (which holds a one-time link) is blanked once sent. Set `ZYVOR_SMTP_URL` (`smtp://user:pass@host:587?tls=required` or `smtps://...`), `ZYVOR_MAIL_FROM` and `ZYVOR_CONSOLE_PUBLIC_URL` on **both the API and the worker**; with no SMTP URL the mailer only logs the message and its link, nothing is delivered, and the sign-in check below is off. Signup emails a verification link; when mail is really delivered, sign-in is refused until it is used (`email_not_verified`), and `POST /v1/signup/resend` sends another. Admins invite people by email (`POST /v1/console/invitations`; seven-day single-use link, a new invitation replaces an older one, revocable); the person chooses their own password on `/accept`. `/forgot` and `/reset` reset a password by emailed link (one hour, single use; ends all sessions; no answer reveals whether an address has an account). Verified end to end in a browser with the worker sending to a local SMTP sink, and in tests against an in-test SMTP server. **Not verified: TLS and username/password login to a real mail server, deliverability (SPF, DKIM, spam), and the k3s and Helm manifests, which do not yet set the SMTP variables.** Links are plain text; there are no HTML templates, no per-organisation sender, and no unsubscribe or notification emails (payment receipts, reminders) yet.

- **Default sandbox (branch `ux/stripe-console`)**: every new organisation's test tenant gets the in-process `sim` provider at signup (`admin::ensure_simulator_account`; refused for live), so a new account can complete a payment with no setup. An existing test tenant can turn it on from the console Sandbox page (admin). The Sandbox page (test mode, finance and admin) lists the outcomes and creates a test payment that is declined, stays pending, has an unknown outcome or succeeds, picked by the UPI handle (`ok@`, `fail@`, `pending@`, `uncertain@`); a succeeded one can be refunded from its page, and an unknown one opens a reconciliation case. Verified in a browser from a fresh signup: succeed, partial refund, unknown outcome. Not built: card, wallet and netbanking test payments in the console (the simulator supports them through the API), settlement and webhook-delivery simulation, test clocks for subscriptions and dunning, and a "reset test data". The simulator is not the Razorpay or Cashfree sandbox: nothing here runs against a real provider. Seen while testing: a payment's timeline can list "Payment captured" after a later refund, because it uses the attempt's last-updated time.

- **Provider connection and the real sandbox (branch `ux/stripe-console`)**: an admin Providers page connects Razorpay or Cashfree (test or live keys per environment), shows the webhook address to paste into the provider's dashboard (from `ZYVOR_PUBLIC_API_URL`), and has a read-only **Check connection** (`POST /v1/provider_accounts/{provider}/check`, a new `Provider::check` on the Razorpay and Cashfree adapters: Razorpay lists one payment, Cashfree looks up an order that cannot exist and treats 404 as "authenticated"). Zyvor refuses a Razorpay key that does not match the environment (`rzp_live_` in test, `rzp_test_` in live) and Cashfree's production address in test, but only when talking to the real provider (a custom address is for simulators). `docs/zyvor/REAL_SANDBOX.md` is the step-by-step runbook and checklist. **Not done: no payment has been taken through Razorpay's test mode or Cashfree's sandbox from this branch, because that needs your test credentials and a public address for the webhooks**; the check is verified only against the local mock. The demo k3s cluster is mock-only and has no ingress.

- **Open items and how to do each**: `docs/zyvor/OPEN_ITEMS.md` lists everything not finished after the self-serve console work (security decisions before any real merchant, real Razorpay and Cashfree sandbox runs, email on real SMTP, sandbox extras, people and roles, console polish, operations), with the file to change and the check for each. `scripts/real-sandbox-check.sh` runs the real-provider checklist from the command line, and the k3s manifest and Helm chart carry optional email settings.

- **Hardening of the self-serve console**: a console session now ends 12 hours after its sign-in however often its key is swapped between test and live (each swap revokes the key it replaces), sign-out revokes the key at the API (`POST /v1/console/logout`), and the worker deletes session keys a day after they end; the console signs each visitor's address with `ZYVOR_ACTOR_SECRET` so the API rate-limits visitors separately (`CONSOLE_TRUST_PROXY_HOPS`); a person's key that the API no longer accepts sends them to sign-in; and with KYC on, a bank account is auto-verified only before the business is submitted and only if the bank's name for it matches. Still open, and a decision for the owner: who approves a merchant before live opens (`docs/zyvor/OPEN_ITEMS.md` 1.1).

- **Zyvor-operated review before live mode**: a merchant whose business details are approved presses "Request live access"; a named Zyvor reviewer (own `zp_` key, made with `zyvor-api platform-reviewer add`) sees what was submitted and the checks that ran and approves, or rejects with a note the merchant is shown and emailed. Only then does the Test / Live switch open Live; a merchant's own approval, key or second admin no longer can. Endpoints: `GET/POST /v1/live_access` (merchant), `/v1/platform/reviews` (reviewers); `scripts/platform-review.sh` for reviewers; gauge `zyvor_live_access_pending`; audit and webhook events `live_access.*`. A reviewer page (`/reviewer`, off unless `CONSOLE_REVIEWER=1`) shows the queue and review and approves or rejects; it was driven in a real browser against a running Zyvor API and Postgres (two reviewers: claim, first and second approval, the refusal when the same reviewer tries twice or another reviewer holds it, take-over; a merchant's legal-details request and a new bank account through the two-reviewer path, and the details written to the test tenant). A second pass covered a change the simulated bank check passed (no second reviewer needed, then escalated in the page), revoke by one reviewer and the refusal when the same reviewer tried to restore it (a different one did), the overdue label on a backdated change, and a stale reviewer cookie. Not tried there: the SLA email and alerts, and Cashfree/Razorpay or a real KYC provider behind any of it (the KYC provider was the simulator). A reviewer can also take live mode away from a business that is already live and give it back (`/v1/platform/reviews/{org}/revoke` and `/restore`, the reviewer page, `scripts/platform-review.sh revoke|restore`): its live side then reads and refunds but takes no new payments or payouts and runs no scheduled debits; test mode is untouched. A bank account added to an approved business is re-reviewed by Zyvor (`live_changes`, `/v1/platform/changes`, reviewer page, gauge `zyvor_live_changes_pending`): its live payouts are held until a reviewer approves, or rejects and removes it. Approvals that warrant it (a check did not pass, no check ran, three asks, or an escalation; `ZYVOR_REVIEW_TWO_PERSON`) need two different reviewers, and every request and held change has a target time (`ZYVOR_REVIEW_SLA_HOURS`, `ZYVOR_CHANGE_SLA_HOURS`) with overdue gauges, alerts, an operator email (`ZYVOR_REVIEW_ALERT_EMAIL`) and due/overdue labels in the queue. A reviewer can take a pending review so only they decide it (`/v1/platform/reviews/{org}/assign`, queue filter, `platform-review.sh claim|release|take-over|assign`); it is a courtesy against duplicated work, not access control, and any reviewer can take over (audited). Giving live mode back needs a different reviewer than the one who revoked it (unless `ZYVOR_REVIEW_TWO_PERSON=never`); the revoke itself stays one person and immediate. An approved business can ask to change its legal details (`POST /v1/onboarding/profile_change`, an Onboarding section, the same change queue and payout hold as a bank account; approval updates the test and live copies; one reviewer decides). A bank-account or legal-details change that nothing checked, or that a check did not pass, needs two different reviewers under the same policy (the first approval keeps the payout hold). A reviewer can escalate a change to ask for a second reviewer. Changes can be held by one reviewer the same way (`/v1/platform/changes/{id}/assign`). **Not built: a rota, re-checking identity after approval (only last-four digits are kept), holding or clawing back money already with the provider.** Existing organisations are not grandfathered: any that reached live under the old rule must be reviewed to switch again. The review is only as strong as the checks behind it (the KYC provider is still a simulator).

- **Cashfree Secure ID for onboarding checks**: `ZYVOR_KYC_PROVIDER=cashfree` (with `ZYVOR_KYC_CASHFREE_ENV`, `_CLIENT_ID`, `_CLIENT_SECRET`) checks PAN, bank account and GSTIN with Cashfree instead of the simulator; anything the provider cannot answer clearly (refused credentials, address not whitelisted, no balance, rate limit, outage, timeout, a name that does not clearly match) is `inconclusive` and goes to a person, never a pass; paid calls are capped at 12 per business per day (`kyc_usage`); only outcomes are stored. `zyvor-api kyc-selftest` runs Cashfree's documented sandbox test inputs against the configured credentials. Written from Cashfree's API reference and tested over HTTP against a local mock that follows it and its sandbox test data. **Not run against Cashfree: that needs Secure ID credentials (and their IP whitelist, balance and the TEST/PROD enablement).** The simulator remains for tests.
