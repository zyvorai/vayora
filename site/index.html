From a tap to your books.

What a customer sees, what the server does behind it, and how the books stay right afterwards. Your own provider account collects and settles the money; Zyvor never holds it.

  1. Scan or tapA counter QR or a payment link opens checkout in the customer's language.
  2. Pick UPI or cardSix languages. The page can pay this one payment and nothing else.
  3. Approve in the UPI appThe customer enters their PIN with their bank. Zyvor never sees it.
  4. Recorded onceA signed webhook from the provider is checked, de-duplicated and posted to the ledger one time.
  5. You are toldYour system gets a signed event. The customer sees "Payment received".

Tap twice, pay once.

Each tap carries an idempotency key that is saved in the same database transaction as the work. A repeat returns what already happened.

Lost the signal? We ask, never re-send.

The attempt is saved before the provider is called. If no answer comes back it becomes unknown, blocks any new attempt, and the worker asks the provider what really happened.

Late or duplicate webhooks are safe.

Every event goes through one state function. State only moves forward, and money always wins: a capture is accepted even after a failure, and flagged for review.

History cannot be rewritten.

The ledger and audit trail reject updates and deletes in the database itself. A mistake is fixed with a reversal, never an edit.

Your providers, one API.

Merchants connect their own Razorpay and Cashfree accounts. A capability matrix stops a payment going to a provider that cannot take it, and every routing decision records why.

Reconciliation turns each unexplained settlement difference into an assigned case, with a plain-language explanation of why the net is what it is.

Three calls. That’s the integration.

Create a payment, start an attempt, verify the webhook.

zyvor · simulated
# amounts are integer minor units (₹499.00 = 49900)
curl localhost:8080/v1/payment_intents \
  -H "Authorization: Bearer zk_test_123" \
  -H "Idempotency-Key: fee-1001" \
  -H "Content-Type: application/json" \
  -d '{"amount_minor": 49900, "external_ref": "FEE-STU-2231"}'

curl localhost:8080/v1/payment_intents/pi_…/attempts \
  -H "Authorization: Bearer zk_test_123" \
  -H "Idempotency-Key: attempt-1001" \
  -H "Content-Type: application/json" \
  -d '{"method": "upi"}'
import { Zyvor } from "@zyvor/node";

const zyvor = new Zyvor({ apiKey: process.env.ZYVOR_API_KEY! });

const intent = await zyvor.intents.create({
  amountMinor: 49900,
  externalRef: "FEE-STU-2231",
});

const attempt = await zyvor.intents.attempt(intent.id, { method: "upi" });
// attempt.route.reasons explains why this provider was chosen
import { verifyWebhook } from "@zyvor/node";

// use the RAW body, not re-serialised JSON
app.post("/webhooks", express.raw({ type: "*/*" }), (req, res) => {
  const ok = verifyWebhook({
    secret: process.env.ZYVOR_WEBHOOK_SECRET!,
    header: req.get("Zyvor-Signature")!,
    rawBody: req.body,
  });
  if (!ok) return res.sendStatus(400);
  // dedupe on event.id: delivery is at-least-once
  res.sendStatus(200);
});

Where it really stands.

What is built, what is verified, and what is not. We would rather say so plainly.

Working
Payments, routing, refundsRazorpay and Cashfree adapters behind a capability matrix; unknown outcomes are resolved, never re-sent. Verified against local provider simulators.
Working
Ledger and reconciliationAppend-only double-entry ledger; settlements, bank lines and cases that explain every difference.
Working
Billing, collections and disputesSubscriptions, usage, proration, milestones, credit notes, ageing, promises to pay and chargebacks.
Working
Links, splits, payouts and GSTPayment links with QR codes and coupons, marketplace splits to vendors, approved payouts with their bookkeeping, GST tax invoices, checkout in six languages.
Working
Security basicsRate limits, expiring and rotatable API keys, a tamper-evident audit chain, TOTP sign-in with roles, tenant isolation in the database. Threat model.
Working
Console, SDKs and CLIMerchant console, @zyvor/node, Python, Go and an OpenAPI spec.
Next
Live provider testingThe adapters follow each provider's public docs but have not yet run against live sandbox accounts.
Not built
Real payouts and mandatesZyvor records and approves payouts but you make the transfer from your bank. UPI AutoPay mandates, instant settlement and GST filing are not built, and the non-English checkout text still needs native review.
Your responsibility
Regulatory statusZyvor does not hold or move funds; your providers do. Whether your deployment needs its own authorisation is a question for counsel. Read the note.
